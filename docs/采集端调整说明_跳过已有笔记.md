# 采集端调整说明:跳过已有笔记(接口 v1.4)

> 面向采集端。工作台已升级到接口 **1.4**(`GET /api/ping` 的 `api_version` 为 `"1.4"`)。完整接口见《采集端接口.md》6.5 节,本文只说明这次要配合改的地方。

## 1. 为什么要改

同一个产品、同一个赛道会反复出稿,搜索出来的大多是工作台已经存过的笔记。现在采集端每次都会把它们逐篇点进详情页再回传一遍:

- 白花时间,一个任务要多跑很久;
- 短时间连续打开大量详情页,更容易触发风控(之前「连续多篇笔记读取失败」就和这个有关);
- 真正新的笔记反而采得少。

工作台这边也已经改成「笔记库优先」:库里相关笔记够多时,任务根本不会下发给采集端;只有不够时才让采集端去补新的。

## 2. 需要改的流程

```
领到任务(skip_known = true)
  → 打开搜索结果列表,收集这一屏的笔记 ID
  → POST /api/notes/known {"ids": [...]}       ← 新增这一步
  → 只点进 new 里的笔记,读详情、回传
  → 新笔记不够 limit 篇:继续往下翻,重复上面三步
  → 够了,或翻到 5 屏 / 扫描 limit × 5 条:结束,回传 done
```

## 3. 细节

| 项目 | 要求 |
|---|---|
| 什么时候查 | 每拿到一屏搜索结果查一次,不要每篇查一次 |
| 一次查多少 | 最多 500 个 ID |
| ID 格式 | 和回传笔记时的 `note_id` 一样 |
| `limit` 怎么算 | 只算新笔记;已有的不占名额 |
| 不够怎么办 | 翻到上限还不够,有多少回传多少,正常返回 `done`,不要标失败 |
| 博主任务 | 同样适用 |
| 任务没有 `skip_known` | 按原来的方式采(兼容旧任务) |
| 查询失败 | 网络错误时重试一次;还失败就按原来的方式采,不要卡住任务 |

## 4. 顺手的建议

- 每篇详情页之间加 2–5 秒随机等待,减少「弹窗数据为空」这类失败。
- 采集忙的时候,至少每 60 秒调一次 `GET /api/ping`,工作台才会一直显示在线。

## 5. 自检清单

- [ ] `GET /api/ping` 返回 `api_version: "1.4"`
- [ ] 领到的任务里能读到 `skip_known: true`
- [ ] 搜索列表的 ID 先经过 `/api/notes/known`,`known` 里的不再点详情页
- [ ] 同一个关键词连续跑两次,第二次回传结果里 `new_in_library` 基本等于回传篇数(说明没有重复采)
- [ ] 新笔记不够时任务照常 `done`
