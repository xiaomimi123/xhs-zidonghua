# 小红书流水线 · 采集端对接文档

| 项 | 内容 |
|---|---|
| 接口版本 | 1.4(`GET /api/ping` 返回 `api_version`) |
| 协议 | HTTP + JSON,UTF-8 |
| 端口 | **18765**(TCP) |
| 鉴权 | 请求头 `Authorization: Bearer <Token>` |
| 工作台负责 | 生成采集任务、接收和存储笔记、去重、分类、拆解、复刻 |
| 采集端负责 | 领取任务 → 在本地打开小红书搜索 → 抓取笔记详情 → 回传 |

---

## 1. 整体流程

```
 工作台(用户选赛道、填关键词)                 采集端
 ───────────────────────────                 ─────────────────────────────
 每个关键词生成一条任务 [pending]
                                   ◄──────── ① GET /api/ping        启动时自检一次
                                   ◄──────── ② GET /api/tasks       每 5~15 秒轮询
 任务标记为 [running],返回任务 ──────────►
                                             ③ 在小红书搜索 query,取前 limit 条,
                                                逐条进入详情页读取正文、图片、互动数
                                   ◄──────── ④ POST /api/notes      回传结果
 入库、去重、自动打标签,
 任务标记为 [done] / [failed]
```

- 任务被领走后只属于这台采集端;**15 分钟内没有回传**,任务会自动退回 `pending`,由下次轮询重新领取。采集端崩溃不会丢任务。
- 每次调用 `/api/ping` 或 `/api/tasks` 都会被记为一次心跳。回传笔记(`POST /api/notes`)也算心跳。管理端「采集监控」里显示每台采集端的在线状态(150 秒内有心跳为在线)。采集端忙着读笔记时,建议至少每 60 秒调一次 `GET /api/ping`。

## 2. 网络与地址(连不上时先看这里)

采集端访问的地址 = `http://<工作台所在电脑的地址>:18765`。根据两边的位置选一种:

| 场景 | 采集端应填写的地址 | 说明 |
|---|---|---|
| A. 采集端和工作台在**同一台电脑** | `http://127.0.0.1:18765` | 直接可用 |
| B. 在**同一个局域网**(同一路由器/公司内网) | `http://<工作台电脑局域网 IP>:18765`,例如 `http://192.168.1.100:18765` | **不能填 127.0.0.1**,那指的是采集端自己那台电脑 |
| C. 不在同一网络(家里/异地/云服务器) | 方式一:两台电脑都装 Tailscale,填工作台的 Tailscale IP(`100.x.x.x`);方式二:工作台部署到有公网 IP 的服务器,填域名或公网 IP | 公网部署时务必配 HTTPS(见项目 README) |

工作台管理员可在 **管理端 → 接口配置 → 采集端对接** 里看到并复制完整地址和 Token(填写「对外地址」后显示的就是采集端该用的地址)。

### 2.1 自检步骤(在采集端那台电脑上执行)

```bash
# 1) 端口通不通:能返回一段 JSON 就说明网络是通的
curl http://<工作台地址>:18765/api/session

# 2) Token 对不对:返回 "ok": true 即对接成功
curl -H "Authorization: Bearer <Token>" "http://<工作台地址>:18765/api/ping?worker=pc-01"
```

### 2.2 排查清单

| 现象 | 原因与处理 |
|---|---|
| 连接超时 / 拒绝连接 | 地址写成了 `127.0.0.1` 而两边不在同一台电脑(见场景 B);或不在同一网络(见场景 C);或工作台没启动(管理员执行 `docker compose ps` 查看) |
| 局域网 IP 也连不上 | 工作台电脑的防火墙拦截了 18765 端口;或两台电脑不在同一网段;或采集端电脑开了代理/VPN 的全局模式,把局域网流量也转走了,需要让局域网地址直连 |
| `401 采集端 token 无效` | 请求头缺失或 Token 不对。格式是 `Authorization: Bearer <Token>`,Bearer 后有一个空格;Token 被重新生成过要换新的 |
| `404 Not Found` | 路径写错,必须带 `/api` 前缀,如 `/api/tasks` 而不是 `/tasks` |
| `404 task_id xx 不存在` | 任务已被用户删除,丢弃该任务继续轮询即可 |
| `422` | 请求体不是合法 JSON,或字段类型不对 |

## 3. 接口一览

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/ping` | 连通性和 Token 自检,记录心跳,不领任务 |
| GET | `/api/tasks` | 领取待采集任务 |
| POST | `/api/notes` | 回传采集结果 / 上报任务失败 |
| POST | `/api/notes/known` | 查询哪些笔记已经在工作台笔记库里(1.4 新增,见 6.5) |

所有接口都必须带 `Authorization: Bearer <Token>`。

---

## 4. GET /api/ping

| 参数 | 必填 | 说明 |
|---|---|---|
| `worker` | 建议 | 采集端名称,如 `pc-01`,多台采集端时用于区分 |

返回:

```json
{ "ok": true, "server_time": "2026-10-31 16:06:55", "worker": "pc-01", "pending_tasks": 3, "api_version": "1.4", "task_types": ["keyword", "title", "author"] }
```

---

> **任务超时与续租**:任务被领走后,15 分钟没有任何动静才会退回待领取。以下任何一种都算「有动静」并重新计时:这个采集端的 `GET /api/ping`(带 `worker`)、`GET /api/tasks`、`POST /api/notes`(包括 `done:false` 的分批回传)、`POST /api/notes/known`。采得慢的长任务,保持每 60 秒 ping 一次就不会被重复领取。

## 5. GET /api/tasks

| 参数 | 必填 | 说明 |
|---|---|---|
| `limit` | 否 | 一次最多领几条,默认 1,最大 20。**建议 1**,做完一条再领下一条 |
| `worker` | 建议 | 采集端名称 |
| `types` | 建议 | 本采集端**支持**的任务类型,逗号分隔,如 `keyword,title,author`。**不传时只会领到 `keyword` 和 `title`,领不到博主任务**——这样没做博主模式的采集端不会领到自己处理不了的任务 |

返回:

```json
{ "tasks": [ { "id": 12, "type": "keyword", "query": "早八通勤妆", "limit": 20, "max_age_days": 180, "note_type": "image", "sort": "popularity" } ] }
```

| 字段 | 说明 |
|---|---|
| `id` | 任务 ID,回传时作为 `task_id` 带回 |
| `type` | `keyword`:按关键词搜索;`title`:按一篇笔记的标题搜索(找到这篇以及相似的笔记);`author`:采集一位博主的笔记(见 5.1) |
| `query` | 要搜索的关键词或标题 |
| `limit` | 需要回传的笔记条数(由管理端「每个任务采集条数」决定,默认 20) |
| `max_age_days` | **只采最近多少天发布的笔记**,默认 180(近半年);`0` 表示不限。博主任务不受此限制。详见《采集端调整说明_近半年与精准采集.md》 |
| `note_type` | `image` 只要图文;`all` 不限 |
| `sort` | `popularity` 最热 / `general` 综合 / `latest` 最新 |
| `skip_known` | 为 `true` 时:已在笔记库里的笔记不用再点进详情页,`limit` 只算新笔记(见 6.5) |

- 没有任务时返回 `{"tasks": []}`,等待后再拉。**建议轮询间隔 5~15 秒**。
- **搜索要求**:按「最热」排序,取前 `limit` 条图文笔记,**必须进入详情页**拿正文全文和全部图片(只有列表页信息时拆解效果会差很多)。

### 5.1 博主任务(`type = "author"`)

用户在工作台输入一位博主,采集这位博主的笔记,拿来拆解 TA 的写法。

| 项 | 约定 |
|---|---|
| `query` | 博主主页链接(如 `https://www.xiaohongshu.com/user/profile/<user_id>`)或小红书号,单行文本,最长 300 字符。**用户可能填任一种,请两种都能识别** |
| `limit` | 最多回传多少篇 |
| 取哪些 | 建议优先取**点赞最高**的 `limit` 篇(拆解需要的是这位博主的代表作);不足 `limit` 篇时有多少回传多少 |
| 视频笔记 | **保留**并标 `"type": "video"`(关键词 / 标题任务里仍然跳过)。工作台会给视频笔记加「视频」标记,**不计入**爆款统计 |
| 每篇笔记 | 都带上 `author`(昵称)和 `author_id`(博主 ID) |
| 失败 | 博主不存在、账号私密、主页打不开等,用 `error` 上报并写明原因,如 `"博主不存在或账号已注销"` |

领取博主任务需要带 `types`:`GET /api/tasks?limit=1&worker=pc-01&types=keyword,title,author`。

## 6. POST /api/notes

### 6.1 标准格式(推荐)

```json
{
  "task_id": 12,
  "done": true,
  "error": "",
  "notes": [ { "...": "笔记字段,见第 7 节" } ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `task_id` | ✅ | 领到的任务 ID |
| `notes` | ✅ | 笔记数组,失败时可以为空数组 |
| `done` | 否 | 默认 `true`。支持分批回传:前面几批传 `false`,最后一批传 `true` |
| `error` | 否 | 非空表示任务失败,如 `"需要登录"`、`"触发验证码"`、`"搜索无结果"`。会显示在工作台上,用户可点重试 |

### 6.2 兼容格式

也可以直接传笔记数组,每条带 `task_id`。工作台按 `task_id` 分组,并把这些任务视为完成:

```json
[ { "task_id": 12, "title": "...", "content": "...", "likes": 56000 } ]
```

### 6.3 上报失败

```json
{ "task_id": 12, "notes": [], "error": "触发滑块验证码" }
```

已经抓到一部分时,可以把已抓到的放进 `notes` 同时填 `error`,已抓到的会正常入库。

### 6.4 返回

```json
{ "ok": true, "results": [ { "task_id": 12, "saved": 18, "duplicated": 2, "new_in_library": 15, "status": "done" } ] }
```

| 字段 | 说明 |
|---|---|
| `saved` | 本次新加入该项目的笔记数 |
| `duplicated` | 该项目里已经有的笔记数 |
| `new_in_library` | 在笔记库里第一次出现的笔记数 |
| `skipped_old` | 因发布时间超出任务 `max_age_days` 被工作台丢弃的笔记数(1.3 新增;`published_at` 缺失的笔记不会被丢) |
| `status` | 任务最终状态:`done` / `failed` / `running`(`done:false` 时) |

---

### 6.5 POST /api/notes/known(1.4 新增)

同一个产品、同一个关键词反复采,搜索结果大多是工作台已经存过的笔记。采集端在**搜索结果列表**拿到一批笔记 ID 后,先问一下哪些是新的,只点进新的详情页:省时间,也少触发风控。

请求:

```json
{ "ids": ["6a8eaa12000000001e00abcd", "6a101fe0000000001d00ef01"] }
```

返回:

```json
{ "known": ["6a8eaa12000000001e00abcd"], "new": ["6a101fe0000000001d00ef01"] }
```

- `ids` 填笔记 ID(和回传笔记时的 `note_id` 一致);一次最多 500 个,超过的忽略。
- 这次调用也算一次心跳。请求里可以带 `?worker=名称`;不带时算到最近活跃的采集端头上。
- 任务带 `skip_known: true` 时:`known` 里的笔记**跳过不采**,继续往下翻,直到采够 `limit` 篇新笔记,或翻到 5 屏 / 扫描 `limit × 5` 条为止;不够也正常返回 `done`。
- 已有的笔记偶尔回传也没关系,工作台按 `note_id` 去重,只刷新互动数据。

## 7. 笔记字段规范

```json
{
  "note_id": "6650a1b2000000001e03c4d5",
  "url": "https://www.xiaohongshu.com/explore/6650a1b2000000001e03c4d5",
  "title": "早八通勤妆10分钟搞定,手残党也能冲",
  "content": "每天只想多睡十分钟?这套底妆+眉眼的极简流程……",
  "author": "小鹿不加班",
  "likes": 56000,
  "collects": "2.1万",
  "comments": 830,
  "cover": "https://sns-webpic-qc.xhscdn.com/xxx.jpg",
  "images": ["https://sns-webpic-qc.xhscdn.com/1.jpg", "https://sns-webpic-qc.xhscdn.com/2.jpg"],
  "tags": ["通勤妆", "早八", "新手化妆"],
  "type": "normal",
  "published_at": "2026-10-20"
}
```

| 字段 | 类型 | 要求 | 说明 |
|---|---|---|---|
| `title` | string | **必填** | 标题原文 |
| `content` | string | **必填(要全文)** | 详情页正文全文,保留原有换行和 emoji;不要截断,不要包含话题标签 |
| `note_id` | string | **必填** | 小红书笔记 ID,用于全局去重。缺失时依次退回用 `url`、标题+正文去重 |
| `likes` | number / string | **必填** | 点赞数。可以传数字,也可以原样传 `"1.2万"`、`"3.4w"`、`"5k"`,工作台会换算 |
| `collects` | number / string | 强烈建议 | 收藏数,格式同上 |
| `comments` | number / string | 强烈建议 | 评论数,格式同上 |
| `url` | string | 建议 | 笔记详情页链接 |
| `images` | string[] | 建议 | 全部配图 URL,按笔记里的顺序。**工作台收到后会立即下载到本地**(见下),请回传刚抓到的新鲜链接 |
| `cover` | string | 可选 | 封面 URL,不传时取 `images[0]` |
| `tags` | string[] / string | 建议 | 话题。数组(不带 #)或字符串 `"#通勤妆 #早八"` 都可以 |
| `author` | string | 可选(博主任务必填) | 作者昵称 |
| `author_id` | string | 可选 | 作者 ID(主页链接里的 user_id)。不传也行,只要传了 `author_url`,工作台会自动提取 |
| `author_url` | string | 建议 | 作者主页链接,如 `https://www.xiaohongshu.com/user/profile/<user_id>` |
| `type` | string | 可选 | `normal` 图文 / `video` 视频。视频笔记在工作台里有标记,且不参与爆款统计 |
| `published_at` | string | 可选 | 发布时间。原样传页面上看到的就行(「编辑于 2025-11-05」「09-02」「3天前」「昨天 12:30」都可以),工作台会统一成 `YYYY-MM-DD`;没写年份的按采集当天推断 |

**图片转存**

- 小红书图片链接带时间戳签名,会过期。工作台收到笔记后**立刻**把封面和全部配图下载到服务器本地,之后页面和导出都用本地副本,链接过期不再影响。
- 所以请**抓到就尽快回传**,不要把链接缓存很久再发。大批量时可以用 `done:false` 分批回传,每抓完几条就先发几条。
- 只接受真实的图片文件(jpg / png / webp / gif / avif),单张不超过 15MB;不是图片(如返回了错误页)、链接已过期(403 / 410)会标记为转存失败,管理端「笔记库」会提示并可一键重试。
- 同一篇笔记**重新采集**时,如果上次有图片转存失败,工作台会用这次的新链接替换并重新转存。已转存成功的图片不会重复下载。
- 工作台会记录下载失败时的 HTTP 状态码,请采集端在联调时留意失败比例,据此测出链接大概多久过期(目前未知)。

**数据说明**

- 同一篇笔记(同一 `note_id`)重复回传不会重复入库:互动数取更大的值,空的正文和图片会被补全,并关联到新的项目。所以**重新采集不用担心重复**。
- 入库时工作台自动记录赛道、关键词、采集任务、采集端名称,并由 AI 打内容类型标签,采集端不用处理分类。
- 「点赞 + 收藏 + 评论」用来给笔记分级(爆款/热门/普通),是拆解的重要依据,请尽量传真实数值。

## 8. 返回码

| HTTP 状态 | 含义 | 采集端处理 |
|---|---|---|
| 200 | 成功 | — |
| 401 | Token 缺失或错误 | 停止轮询,检查配置 |
| 404 | 路径错误,或 `task_id` 不存在 | 路径错误需修正;任务不存在则丢弃 |
| 422 | 请求体格式错误 | 检查 JSON |
| 5xx / 网络错误 | 工作台异常或重启中 | 等待 10~30 秒后重试;已领的任务 15 分钟后会自动退回 |

## 9. 参考实现

项目里的 `tools/collector_demo.py` 是完整的参考实现(自检、轮询、回传、失败上报),把其中 `fetch_notes()` 换成真实的抓取逻辑即可。不抓取、只联调接口时:

```bash
python tools/collector_demo.py --server http://<工作台地址>:18765 --token <Token> --worker pc-01 --mock
```

核心循环:

```python
import time, httpx

cli = httpx.Client(base_url="http://<工作台地址>:18765", timeout=30,
                   headers={"Authorization": "Bearer <Token>"})
cli.get("/api/ping", params={"worker": "pc-01"}).raise_for_status()   # 启动自检
TYPES = "keyword,title,author"   # 声明自己支持的任务类型;不声明就领不到博主任务

while True:
    tasks = cli.get("/api/tasks", params={"limit": 1, "worker": "pc-01", "types": TYPES}).json()["tasks"]
    if not tasks:
        time.sleep(10)
        continue
    t = tasks[0]
    try:
        notes = fetch_notes(t["type"], t["query"], t["limit"])          # 你的抓取逻辑
        body = {"task_id": t["id"], "notes": notes, "done": True}
    except Exception as e:
        body = {"task_id": t["id"], "notes": [], "error": str(e)}
    cli.post("/api/notes", json=body)
```

## 10. 联调步骤

1. 工作台管理员:管理端 → 接口配置 → 采集端对接,填写「对外地址」,把地址和 Token 发给采集端。
2. 采集端:执行第 2.1 节的两条 `curl`,确认返回 `"ok": true`。
3. 采集端:跑一次 `collector_demo.py --mock`,确认管理端「采集监控」里出现这台采集端且显示在线。
4. 工作台用户:在用户端新建一个赛道项目,填 1 个关键词。
5. 采集端:真实抓取并回传。
6. 双方核对:管理端「笔记库」里笔记数量、正文是否完整、互动数是否正确、图片能否显示。

## 11. 需要采集端确认的事项

请采集端逐条回复,便于两边对齐:

1. 部署位置:采集端和工作台是同一台电脑、同一局域网,还是异地?(决定第 2 节用哪种地址)
2. ~~能否稳定拿到正文全文、收藏数、评论数~~ **已答复**:正文全文、点赞、收藏、评论都能稳定拿到。
