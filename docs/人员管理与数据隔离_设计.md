# 人员管理与数据隔离 · 设计稿

> 状态:**P1 已完成(2026-11-11),尚未部署到线上容器。**
>
> 已拍板:① 历史任务、稿子、Live 任务全部归管理员,不分给任何员工(迁移不回填);② 产品全员共享(不加 owner);
> ③ 达人库全员可见,员工「认领跟进 / 放手」,负责人记员工显示名,别人认领的不能抢;④ 按账号复盘放到 P3;⑤ 不做组长,只有管理员和员工两种角色。
>
> 实现与下文的差异:产品不加 `owner_id/shared`;`staff` 表没加 `role/deleted_at`(删除员工仍是硬删,数据保留,owner_id 不会被同名新账号继承);
> 归属校验做成 `auth.require_user` 里的统一守卫(`app/scope.py` 的 `guard`),按路由路径参数名自动校验,不用逐个接口改。
> 测试:`evals/cases/iso_owner.py`(含接口登记检查)。

## 一、现状

| 已有 | 缺的 |
|---|---|
| `staff` 员工表:账号、姓名、密码哈希、启用、`token_ver`(改密码或踢下线后旧会话失效) | **数据不分人**:`/api/runs`、`/api/library`、`/api/projects`、草稿、拆解卡、Live 图、产品的列表和详情都返回全部数据 |
| 管理端人员管理:新增、停用、重置密码、踢下线、删除 | 按 id 访问不校验归属,改 URL 里的数字就能看或删别人的稿子 |
| 登录限流(同一 IP 10 分钟失败 5 次就锁定)、签名 Cookie | `/images/{文件名}`、`/download/{压缩包名}` 只要知道文件名就能拿到,而压缩包名是时间戳,可以猜出来 |
| `projects.created_by` 记录了发起人**账号名** | 用账号名关联不可靠:员工删了以后,再建一个同名账号会继承旧数据 |
| | 员工不能自己改密码 |
| | 删除员工后,他的数据就没有归属了 |

## 二、数据怎么分:三类

| 类别 | 包含的数据 | 员工能看到 | 管理员能看到 |
|---|---|---|---|
| **个人私有** | 任务(projects)及其下面的采集任务、拆解卡、草稿/成品、一键生成进度;Live 图任务;产品;导出包;生成的图片 | 只看到自己的 | 全部,可以按人筛选 |
| **团队共享(员工只读)** | 笔记库(采集到的爆款,按 uid 全局去重)、赛道、合规词库、知识库、千帆数据看板 | 都能看到 | 都能看到,可以编辑 |
| **团队共享(多人协作)** | 达人库:人人都能看,`owner` 字段记录跟进人 | 都能看到,可以认领 | 都能看到 |

**笔记库为什么共享**:同一篇爆款只采集一次,每个任务通过 `project_notes` 关联引用。如果按人拆开,同一篇笔记会被重复采集,还会让采集端多跑很多活。真正属于个人的是「哪个任务引用了哪些笔记」,而这个关联本身已经挂在任务下面了。

## 三、表结构改动(迁移 `_m011_owner`)

```sql
-- 归属统一用 staff.id;NULL = 管理员或历史数据(员工看不到,只有管理员能看到)
ALTER TABLE projects  ADD COLUMN owner_id INTEGER;   -- 草稿、拆解卡、采集任务、一键生成都通过 project_id 继承归属
ALTER TABLE live_jobs ADD COLUMN owner_id INTEGER;   -- Live 任务可以没有对应稿子,所以要单独记录
ALTER TABLE products  ADD COLUMN owner_id INTEGER;
ALTER TABLE products  ADD COLUMN shared INTEGER DEFAULT 0;  -- 管理员可以把公司产品设成全员可用
CREATE INDEX ix_projects_owner ON projects(owner_id);
CREATE INDEX ix_live_owner     ON live_jobs(owner_id);

-- 员工表补充字段
ALTER TABLE staff ADD COLUMN role TEXT DEFAULT 'staff';     -- 先只有 staff,将来可以加 lead(组长)
ALTER TABLE staff ADD COLUMN deleted_at TEXT DEFAULT '';    -- 软删除:账号名不能复用,数据也不会成为无主数据

-- 导出记录(替代内存里的 JOBS,重启后也能下载,并且可以校验归属)
CREATE TABLE exports(id TEXT PRIMARY KEY, owner_id INTEGER, zip TEXT, draft_ids TEXT,
                     created TEXT DEFAULT CURRENT_TIMESTAMP);
```

**历史数据回填**:
- `projects.owner_id`:按 `created_by` 账号名找到对应员工的 id 回填;找不到的(`admin`、空值、已删除的员工)保持 NULL,归到管理员名下。
- `live_jobs`:有 `draft_id` 的按稿子所属任务回填;`created_by` 里存的是**姓名**,只有能唯一对上时才回填,否则保持 NULL。
- `products`:按引用它的任务来回填;被多人用过的产品设成 `shared=1`。
- 迁移前自动备份数据库(现有迁移机制已经会做)。

**草稿表不加 owner_id**:归属只记在 projects 一个地方。草稿通过 `project_id` 查找归属,避免两处数据不一致。成品库本来就 JOIN 了 projects,不会多一次查询。

## 四、后端怎么拦:集中在一个文件,不散写在各个接口里

新增 `app/scope.py`:

```python
def me() -> dict            # 当前登录人,来自 auth.CURRENT;管理员为 {"id": None, "admin": True}
def owner_sql(alias="p")    # 返回 ("1=1", []) 或 ("p.owner_id=?", [sid]),拼到列表查询里
def own_project(pid)        # 找不到 / 不是自己的 → 都返回 404(不说「无权限」,避免泄露这个 id 存在)
def own_draft(did)          # draft → project → owner
def own_playbook(bid) / own_task(tid) / own_live(jid) / own_product(pid)
def own_image(name)         # 生成图文件名是 d{draft_id}_...:解析出 draft_id 再走 own_draft;解析不出来的,员工一律 404
```

套用规则:
1. **列表接口**(runs、projects、library、loop、live/jobs、products):WHERE 条件里拼上 `owner_sql()`,数量统计(`/api/runs/count` 等)也要拼。
2. **带 id 的接口**(大约 40 个 `{pid}`/`{did}`/`{bid}`/`{tid}`/`{jid}` 路由):第一行调用 `own_xxx(id)`。
3. **新建**:`_new_project`、Live 任务、产品写入 `owner_id = me().id`。
4. **后台流程**(autorun、worker、loop.spawn 自动复刻):不依赖请求上下文,新数据继承**来源任务**的 owner_id。比如爆款回流生成的新任务,仍然属于原作者。
5. **文件**:`/images/{name}` 走 `own_image`;`/note_images` 属于笔记库,保持共享;`/download/{zip}` 先查 `exports` 表核对归属,压缩包名加随机串,不能再靠猜。
6. **管理员**:`owner_sql` 直接放行;管理端列表加「按员工筛选」下拉框。

### 防止以后新接口漏拦

在 `evals` 里加一个路由覆盖测试:遍历所有 `/api/*` 路由,每条必须登记成「按归属校验」「共享只读」「公开」三类之一,出现未登记的路由测试就失败。再加一个隔离用例:员工 A 建任务,员工 B 去访问 A 的每个 id 都应该得到 404。按[测试别碰真实任务队列]的约定,这个测试只在临时容器里跑,不调用 `GET /api/tasks`。

## 五、人员管理(管理端)

| 功能 | 说明 |
|---|---|
| 员工列表 | 已有。补充显示:任务数、成品数、近 7 天生成篇数和生图张数(用来估算成本)、最近登录时间 |
| 新增 / 停用 / 重置密码 / 踢下线 | 已有,不改 |
| **删除 → 改为「离职交接」** | 有数据的员工不能直接删。先选择「转给某人」(批量改 owner_id),或者「转给管理员」,然后再软删除 |
| 按人查看 | 点击员工 → 进入只显示他的任务和成品的视图(复用员工端页面,带 `?as=sid`,仅限管理员) |
| 用量上限(可选) | 每人每天最多生成多少篇、生图多少张,超出后提示联系管理员,防止有人一次刷掉大量额度 |

员工端补充:侧栏底部的头像菜单里加「修改密码」(需要输入原密码,改完后 `token_ver+1`,其他设备自动下线)。

**旧的「通用访问密码」模式**:建了员工账号之后已经自动失效。建议从界面上去掉,因为用通用密码登录的人建的任务没有归属,和「每人独立数据」矛盾。代码可以先保留,用来兼容还没建员工账号的部署。

## 六、登录页:左右分屏

效果稿见 `docs/设计稿/登录页.html`(浏览器直接打开就能看)。

- **左侧品牌区(约 55%)**:品牌色渐变背景,上面放产品名和一句定位,中间是核心闭环的四步(批量复刻 → 发帖测试 → 数据归集 → 爆款继续复刻),下方是几张错落的「笔记卡片」做装饰。

- **管理端 `/admin` 登录**:用同一套布局,标题改成「管理后台」,左侧换一种颜色,方便区分。
- **行为不变**:仍然调用 `/api/login`,限流和报错文案都保持现有的。
