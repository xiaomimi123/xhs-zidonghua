# 给采集端的一页说明:有一个新接口需要你们调用(v1.4)

> 这份是前面《采集端调整说明_跳过已有笔记.md》的精简版,只写要做的事和怎么验证。如果你们觉得「没有新内容」,请先按第 3 节自测一下。

## 1. 要做的事(只有一件)

**每拿到一屏搜索结果的笔记 ID,先调用一次下面这个接口,只点进 `new` 里的笔记,`known` 里的跳过。**

```
POST http://<工作台地址>:18765/api/notes/known
Authorization: Bearer <Token>
Content-Type: application/json

{"ids": ["6a8eaa12000000001e00abcd", "6a101fe0000000001d00ef01"]}
```

返回:

```json
{"known": ["6a8eaa12000000001e00abcd"], "new": ["6a101fe0000000001d00ef01"]}
```

- `ids` 就是你们回传 `POST /api/notes` 时的 `note_id`;一次最多 500 个。
- `known` 里的笔记工作台已经存过了,**不用再点进详情页读取、也不用回传**。
- 任务里的 `limit` 现在**只算新笔记**:`known` 的不占名额,继续往下翻,直到采够 `limit` 篇新笔记,或翻了 5 屏 / 扫描了 `limit × 5` 条为止。翻完不够也正常返回 `done`。
- 领到的任务里会带 `"skip_known": true`,带了就按上面做;没带就按原来的做。

## 2. 为什么需要

同一个产品反复做,搜索结果大多是工作台已经存过的笔记。现在每个任务的 5~20 条里,大半是重复的,工作台看到的**新增笔记是 0**:白花时间,还容易触发「连续多篇笔记读取失败」。

## 3. 怎么自测(1 分钟)

```bash
curl -s -X POST "http://<工作台地址>:18765/api/notes/known" \
  -H "Authorization: Bearer <Token>" -H "Content-Type: application/json" \
  -d '{"ids": ["随便填一个你们之前回传过的 note_id", "一个不存在的 id"]}'
```

应该看到第一个在 `known`、第二个在 `new`。

## 4. 工作台这边怎么确认你们已经在用了

管理端「采集监控」的采集端列表里有一列「**跳过已有笔记**」:
- 显示「未使用」= 工作台还没收到过你们的调用;
- 显示「已使用 · N 次 · 查过 X 篇,其中 Y 篇已有」= 对接成功。

## 5. 顺手建议(可选)

- 每篇详情页之间随机等待 2~5 秒,「弹窗数据为空」会少很多。
- 采集忙的时候,至少每 60 秒调一次 `GET /api/ping`,工作台才会一直显示在线。
- 「最近 180 天没有符合条件的笔记(16 篇超出时间范围)」这种情况,可以直接按**最新**排序再搜一遍(工作台重试这类任务时会自动把任务的 `sort` 改成 `latest`)。
